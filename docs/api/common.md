# SamPay API Standards

## Overview

This document defines the common API standards followed by every public API exposed by SamPay.

The objective is to provide a consistent developer experience across all services while ensuring reliability, security and maintainability.

---

# API Versioning

Current API version:

```text
v1
```

Base URL

```text
/api/v1
```

Example

```http
POST /api/v1/payments
```

---

# Authentication

All protected APIs require a valid JWT Access Token.

```http
Authorization: Bearer <access_token>
```

Unauthenticated APIs:

- Login
- Refresh Token

---

# Content Type

Every request and response use JSON.

```http
Content-Type: application/json
Accept: application/json
```

---

# Idempotency

All write operations must include an Idempotency Key.

Applicable methods:

- POST
- PATCH
- DELETE

Header

```http
Idempotency-Key: 2ec5ab9d-a4c7-4e67-b85d-3b0d8cbdd32b
```

If the same request is received multiple times with the same Idempotency Key, SamPay returns the previously generated response without executing the business operation again.

---

# Request Structure

Request bodies use JSON.

Example

```json
{
  "amount": 100000,
  "currency": "INR"
}
```

Money is always represented using the smallest currency unit.

Example

```text
₹1,000

↓

100000 paise
```

---

# Response Structure

Every API response includes a unique `request_id`.

The `request_id` is generated by SamPay for every incoming request and is used for tracing, debugging and customer support.

---

## Success Response

```json
{
  "success": true,
  "request_id": "d3d5f6d8-1d62-45be-b98d-c05d6a9d0db7",
  "data": {},
  "meta": {}
}
```

---

## Error Response

```json
{
  "success": false,
  "request_id": "d3d5f6d8-1d62-45be-b98d-c05d6a9d0db7",
  "error": {
    "code": "INSUFFICIENT_BALANCE",
    "message": "Wallet balance is insufficient."
  }
}
```

---

# Request ID

Every request processed by SamPay is assigned a unique `request_id`.

The same `request_id` is:

- Included in the API response.
- Logged by all internal services.
- Used for distributed tracing.
- Used for debugging and customer support.

Clients should provide the `request_id` when reporting issues to simplify troubleshooting.

# Pagination

All list APIs support pagination.

Example

```http
GET /payments?page=1&page_size=20
```

Response

```json
{
  "success": true,
  "request_id": "d3d5f6d8-1d62-45be-b98d-c05d6a9d0db7",
  "data": [],
  "meta": {
    "page": 1,
    "page_size": 20,
    "total_records": 150,
    "total_pages": 8
  }
}
```

---

# Sorting

Example

```http
GET /payments?sort=created_at&order=desc
```

Supported values

```text
asc
desc
```

---

# Filtering

Example

```http
GET /payments?status=COMPLETED
```

Multiple filters may be combined.

Example

```http
GET /payments?status=COMPLETED&merchant_id=<merchant_id>
```

---

REST resources use plural nouns.

Examples

```text
/merchants
/users
/payments
/payouts
/refunds
/settlements
/linked-bank-accounts
```

---

# UUIDs

All internal resources use UUID Version 4.

Example

```text
d3d5f6d8-1d62-45be-b98d-c05d6a9d0db7
```

---

# Time Format

All timestamps are stored and returned in UTC using ISO-8601.

Example

```text
2026-08-03T10:30:45Z
```

---

# Currency

Version 1 supports:

```text
INR
```

All monetary values are represented using the smallest currency unit (`BIGINT`).

Example

```text
₹500.75

↓

50075
```

# Rate Limiting

Public APIs may be rate limited.

When the rate limit is exceeded, SamPay returns:

```http
429 Too Many Requests
```

---

# Security

- All APIs must be served over HTTPS.
- JWT Access Tokens must only be sent using the `Authorization` header.
- Sensitive information must never be included in URLs.
- Sensitive information must never be logged.
- Every authenticated request must validate token expiry.
- All write APIs require an `Idempotency-Key`.

---

# API Design Principles

Every API should:

- Follow REST principles.
- Use meaningful resource names.
- Return consistent response structures.
- Use appropriate HTTP status codes.
- Validate all input before processing.
- Support idempotency for write operations.
- Never expose internal implementation details.
- Never expose sensitive information.
- Return a unique `request_id` for every request.
